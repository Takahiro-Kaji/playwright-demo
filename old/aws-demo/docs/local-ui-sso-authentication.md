# ADR: SSO認証を伴うローカルPlaywright UI試験

- 記録日：2026-11-01（JST）
- 状態：**合意方針。storageState方式は第一候補であり、実環境での成立は未検証。**
- 今の環境ではSSO実機検証をしていない。認証状態の保存・復元、失効時の判定も未実装。
- 背景：ChatGPT「結合試験スクリプト作成」（会話ID：6ae47b21-5d4c-83e8-86ce-77299e92a039）の合意を、前提との差分から再検討できる記録として残す。

## 1. 決定と対象範囲

UI試験は手元PCのPlaywrightからGoogle Chromeを起動して実行する。**今回はMFAなし。SSO自体は試験対象外で、業務ケースのGivenより前に成立させる共通の試験実行前提条件**とする。認証画面の振る舞いや認証強度を業務ケースの合否対象にしない。バッチ専用ケースにはChrome認証を要求しない。

最初にPlaywrightが独立起動するChromeで人がSSOログインし、認証状態をローカル保存する。その状態を新しいブラウザコンテキストに読み込み、再利用できるか確認する。成立した場合だけ各UI試験へ適用する。通常利用しているChromeのログイン状態が、自動的にPlaywrightへ共有されるとは考えない。

この決定はUI接続の認証に限る。[実対向APIを手元PCからGETする認証](integration-test-strategy.md#9-未解決事項と実装から確認するだけの事項)は別途未確認であり、UIの認証成功をもってAPI取得権限の確立とはしない。

## 2. 事実・前提・推測・未確認

### ユーザーの観察として残す事実

「通常のChromeでは再ログインされないが、シークレットモードでは再認証が走る」というユーザーの観察がある。本作業で再現確認した事実ではない。観察日時、セッション経過時間、端末・Chrome設定等の詳細は未確認。

### 採用する前提

- ローカルPC・Google Chromeを使い、今回はMFAを要求しない想定。
- SSOは試験対象外の共通実行前提条件。
- 認可された試験用アクセスを利用し、企業の端末管理・IdPポリシーに従う。
- OktaまたはMicrosoft Entra IDを候補として想定するが、**実際のプロバイダー、認証方式（OIDC／SAML等）、SDK・キャッシュ設定は未確認**。

### 推測と未検証事項

観察はブラウザ内の状態による認証維持と整合するが、**Cookieに保存されている証拠にはならない**。Cookie、Local Storage、Session Storage、IndexedDB、ブラウザプロファイル、OS・端末の認証状態のどれが必要か、組み合わせかは未検証。IdPのセッションと業務アプリのセッションも区別して確認する。

製品名だけで保存先や再利用可否を決めない。storageStateで十分か、端末・プロファイルへの依存があるか、保存可能な状態でもIdPが再認証を要求するかは実環境で確認する。

## 3. 第一候補と採用理由

第一候補は**初回手動SSOログイン → storageState保存 → 新しいコンテキストで再利用**。業務ケースへSSO操作を散らさず、ケースごとのブラウザ状態分離を維持できるため採用する。ただし、認証状態の保存はセッションの有効期限延長やポリシー制限の解除にはならない。

Playwrightの保存・再利用の基礎はCookieとLocal Storage。Session Storageは標準のstorageState保存対象に含まれない。IndexedDBが必要な場合は、対応版で `indexedDB: true` を明示して保存する（v1.51以降）。これはPlaywrightの機能であり、対象アプリがどれを使うかは別の未確認事項。
参照：[公式認証ガイド](https://playwright.dev/docs/auth)、[storageState API](https://playwright.dev/docs/api/class-browsercontext#browser-context-storage-state)。

## 4. 実環境での最小検証手順

以下は実装・検証する手順であり、実行済みの手順ではない。

1. 対象環境、業務URLのorigin（scheme・host・port）、試験用アカウントの権限、ネットワーク到達性、Chrome・Playwrightの実導入版を確認する。認証確認は業務データやモックを変更する前に行う。
2. `chromium.launch({ channel: 'chrome', headless: false })` でPlaywright専用のChromeを独立起動し、新しいコンテキストで対象業務URLを開く。普段のChromeプロファイルを指定しない。
3. 人がそのChrome画面でSSOログインする。今回はMFAなしの想定。実際に要求された場合は前提との差分として記録し、方針を再検討する。
4. リダイレクト完了と、対象固有の認証済み業務画面・必要な権限を確認する。IdP画面を抜けたことやHTTP 200だけで成功としない。成功判定のURL・locator等は実アプリから確定する。
5. 認証成立後に `await context.storageState({ path: '.local/auth/ui-user.json' })` で保存する。保存先はGit除外し、ディレクトリ0700・ファイル0600相当の本人だけが読める権限にする。IndexedDB依存が判明した場合は `indexedDB: true` を追加して再保存する。
6. 元のコンテキストを閉じ、`browser.newContext({ storageState: '.local/auth/ui-user.json' })` で新しいコンテキストを作る。同じoriginの業務URLへアクセスし、手動再ログインなしで同じ業務画面・権限が成立するか確認する。元のページを使い続けただけでは再利用成功にしない。
7. Chrome自体も終了・再起動し、保存済みファイルだけを読み込んで同様に確認する。本試験と同じ起動モード（現行設定はheadless）でも確認する。コンテキスト間の再利用と、別プロセス・後日の再利用の結果を分ける。
8. 成功したらUI試験の共通準備で読み込み・有効性確認し、成立後にGiven / When / Then / Afterを開始する。各ケースで新しいコンテキストを使う。業務ケースの前に適用範囲の各originで確認し、別リージョンや別ポートへ認証が無条件に共有されると仮定しない。

再ログイン画面への遷移があっても、操作不要で最終的に認証済み業務画面が成立する場合は、その経路を記録する。「IdPへ一切遷移しない」を必須条件にはしない。

## 5. 失敗時の切り分けと代替手段

一度に複数条件を変えず、初回手動ログイン、新コンテキスト、Chrome再起動、本試験の起動モードのどの段階で失敗したか確認する。

- **手動ログイン自体が成立しない**：URL、ネットワーク、アカウントの利用可否・権限、端末登録、実際のIdP条件を確認する。状態保存方式の問題と決め付けない。認証・権限の担当者と許可された接続方法を確認する。
- **保存タイミング／origin／Cookie条件の相違**：認証完了前の保存、別環境のファイル、scheme・host・portやCookieのdomain・path・Secure・SameSite条件を確認する。メタデータと結果だけを記録し、値をログへ出さない。
- **Session Storage依存**：実アプリの実装・設定を確認し、依存が確かなら必要なorigin・キーだけを別のローカル秘密ファイルへ保存し、ページスクリプト実行前の `addInitScript` 等で復元する方式を検討する。対象originを完全一致で限定し、IdPを含む全originへの一律注入はしない。タブ単位・ポップアップ経由の動作も確認する。根拠なくストレージ全量を複製しない。
- **IndexedDB依存**：実導入版と保存オプションを確認し、対応版の `indexedDB: true` で再保存して再検証する。保存対象へ加えても再利用を保証しない。
- **プロファイル／端末依存**：storageStateでは引き継げない状態が必要なら、`.local/chrome-profile/` 等の試験専用userDataDirを使うpersistent contextを検討する。普段のChromeプロファイルの流用・コピーはしない。専用プロファイルもGit除外・秘密情報扱いとし、同時利用を避け、ケース間に残る状態の初期化を設計する。端末証明書・OS連携等への依存はプロファイルだけで解決するとは限らない。
- **IdPポリシーによる制約**：再認証頻度、条件付きアクセス、管理端末・ブラウザの要件、セッションの持出し制限等を確認する。制限を無効化・迂回しない。許可された専用端末／試験用アクセスか、実行の都度手動認証して同じ実行内だけ利用する方式を検討する。
- **セッション失効・サーバー側無効化**：古いファイルを削除し、手動再ログイン後に再保存・再確認する。繰返し失効するなら有効期間と実行所要時間を比較し、実行単位の認証準備を検討する。認証ファイルに有効そうな期限が残っていても、サーバー側で無効なことがある。

代替案も小さい検証で成立を確認してから採用する。persistent contextの仕様と通常Chromeプロファイル利用の制限は[公式API](https://playwright.dev/docs/api/class-browsertype#browser-type-launch-persistent-context)を参照する。

## 6. 判定と中断

- 開始前の認証・権限が成立しない場合、**業務試験FAILではなく「前提条件未成立・未実施」**。既存の集約ルールでは必須項目を未確認とし、理由を前提不成立／未実施として記録する。全体PASS・正常完了にしない。skipだけで全体が成功になる実装にしない。
- 認証成立後の業務操作・表示・DBの不一致は、既存の期待結果に基づき判定する。任意の401・403・画面エラーを全て認証失効扱いにしない。実際の失効か業務権限・アプリ不具合かを切り分け、根拠が足りなければ未確認を残す。
- 試験途中に認証が失効して後続の期待結果を確認できない場合、確認済みの判定を残し、未実施部分を認証前提不成立による未確認として中断する。すでに確認した業務不一致を消さない。実施済み変更の復元・復旧状態は別に記録する。
- 再認証後に変更操作を自動で再送しない。既存操作の成立・DB状態・復元結果を確認してから再実行する。

共通準備は認証の寿命管理と結果記録を担い、業務画面のlocatorや権限の成功条件は対象固有側に置く。[設計・実装ルール](design-and-implementation-rules.md)の責務分離と判定・復元ルールに従う。

## 7. 秘密情報と証跡

SSOアカウントの認証情報、Cookie値、アクセストークン・リフレッシュトークン、セッション値は**Git・GitHub・ログ・試験添付へ含めない**。認証状態ファイルと専用プロファイルは本人のローカルだけに置く。`.local/` は現行 `.gitignore` で既に除外済み。追加前に `git check-ignore .local/auth/ui-user.json .local/chrome-profile/` 等で確認する。Git除外はログ流出防止やアクセス制限の代わりにはならない。

認証準備中はtrace・動画・スクリーンショット・HAR等の記録を無効にし、認証レスポンスやstorageStateをconsole出力しない。認証コード／トークンを含み得るURLのクエリ・フラグメント、Authorization・Cookie・Set-Cookie、レスポンス本文をそのまま証跡に残さない。本試験側にも同じ禁止を適用する。

現行デモは失敗時trace・スクリーンショットを保存し、応答の全ヘッダー・本文を証跡へ添付する。このまま実SSO対象へ転用せず、SSO適用前に認証情報が入らない許可リストによる記録と、保存機能の無効化・制御を実装する。今のコードで秘密情報の排除が保証されているとはしない。

認証状態は不要時・失効時に削除し、必要時に再作成する。実機調査では値を転記せず、保存先の種類、依存の有無、成否と差分だけを記録する。

## 8. 方針を再検討する条件と記録方法

次のいずれかで「storageStateだけで十分」という仮説を見直す。

- 新しいコンテキストまたはChrome再起動後に、認証済み業務画面を再現できない。
- Session Storage／IndexedDB等の追加状態、プロファイル・端末への依存が判明した。
- IdPポリシーで状態再利用が認められない、または実行時間内に失効が頻発する。
- MFA要求、実際のプロバイダー・認証方式、必要権限等が採用前提と異なる。
- 専用プロファイル方式でケース分離・再現性を維持できない、または秘密情報を証跡から除外できない。

差分を記録して方式を選び直す。試行を重ねて失敗を隠したり、SSOを業務ケースのFAILへ押し込んだりしない。

追記する検証記録には、実施日、コード版、Playwright／Chrome版、対象環境の識別子、確認できたIdP・認証方式、起動モード、手動認証の成否、新コンテキスト／再起動後の成否、失効の有無、当初の前提との差分、選んだ代替案と根拠、未確認事項を残す。秘密値・生の認証URLは記録しない。

## 9. 現行リポジトリとの整合と残作業

確認時点の `package.json` は `@playwright/test: ^1.56.0`、`playwright.config.cjs` は `channel: 'chrome'`、`workers: 1`、`retries: 0`、`headless: true`。これは依存宣言・設定の確認であり、実導入版やSSO動作の確認ではない。

現行デモにはSSO手動認証の入口、storageStateの保存・読込み、認証前提の有効性判定はない。本変更は資料と参照リンクの追加のみ。次は秘密情報を残さない最小検証の入口を実装し、上記手順を実SSO環境で確認して結果を本記録へ追記する。**本資料の保存をもってSSO対応済み・実機検証済みとはしない。**
