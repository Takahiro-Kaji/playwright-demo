# 設計を検証するための公式資料メモ

確認日：2026-10-31 JST。今回の耐久性・拡張性・使いやすさに直結する3テーマに絞った。以下の「採用」「受入」「再検討条件」は、このリポジトリへの設計判断であり、公式資料が指定するディレクトリ構成ではない。最新Web文書を参照しているため、採用中の依存版での実行確認も必要である。

## 1. 後処理の寿命と時間予算

公式根拠：[Playwright Fixtures](https://playwright.dev/docs/test-fixtures#execution-order)、[Timeouts](https://playwright.dev/docs/test-timeouts#test-timeout)。fixtureは`await use()`の前後に準備・終了処理を置き、依存先は依存元より先に準備し後に破棄される。テスト本体終了後、fixture teardownとafterEachには本体と別の時間予算がある。fixture自身のtimeoutも設定できる。

**比較した選択肢：** Aは所有する変更・復元・証跡をケース単位fixtureで回収し、Given／When／Thenはケースから読める形にする。Bは通常関数とケース本体のtry/finallyで完結させる。Bは短いケースの流れを追いやすいが、本体timeout時のfinallyはPlaywrightの後処理予算をそのまま利用する位置ではない。対象固有の準備まで巨大fixtureへ移すAの使い方も、ケースの理解を妨げる。

**採用：** 寿命管理はA、業務順序の可読性はBの利点を残す。現在の復元fixtureはこの方向。C03の説明は「PlaywrightにAfter時間がない」ではなく「本体finallyに復元を置いたため、fixture／afterEachの別予算を利用できなかった」とする。独立60秒は今回の2対象の通信上限から選ぶ値であり、普遍的な既定値ではない。

**具体的な受入：** 本体の前提失敗・timeout、復元失敗、両方の失敗で、全復元対象への試行、元失敗と復元結果、証跡、非成功終了、後続停止を確認する。復元通信にも期限を持たせ、後処理予算を使い尽くして無限に待たない。fixtureへ登録する前に変更する経路を残さない。強制終了をfixtureが保証するとは記述しない。

**再検討条件：** 対象数や復元手順が増え予算が不足した時、UIとバッチの独立した寿命を組み合わせる時にfixtureの依存と予算を分ける。業務ごとの継承階層や独自テストランナーは増設しない。

## 2. ブラウザーの隔離と共有システムの隔離

公式根拠：[Playwright Isolation](https://playwright.dev/docs/browser-contexts)、[Parallelism](https://playwright.dev/docs/test-parallel#limit-failures-and-fail-fast)、[Retries](https://playwright.dev/docs/test-retries#failures)。標準のBrowserContextはブラウザー状態をケース間で分ける。失敗時はworkerを交換して後続試験を続行する仕組みがあり、workersを1にしてもfail-fastとは異なる。maxFailuresは未実行ケースの停止に使える。

**比較した選択肢：** Aは共有モック・共有DBを前提に、逐次・自動retryなし・最初の失敗で停止する。Bはケース／workerごとにDBとモックも隔離し、並列を許可する。Bは規模拡大に有利だが、runIdやBrowserContextだけでは全量同期や共有モックを隔離できない。既存の共有環境へBの設定だけ入れると、競合や復元の誤りが増える。

**採用：** 現段階はA。workers:1、retries:0、maxFailures:1を一組として扱い、モックの条件付き変更と復元で他者更新を上書きしない。標準ブラウザーfixtureを使い、バッチだけのケースはpageを要求しない。これはどんな安全な独立ケースも永遠に逐次実行するという方針ではない。

**具体的な受入：** 失敗後にsentinelケースが走らないこと、同じstatusでもversionが変われば旧所有者が復元しないこと、再起動・応答喪失で所有不明を記録し非成功になることを確認する。共有DBやAWSの状態がworker交換で戻ったとは主張しない。実行入口・手順書のオプションで停止／retry方針を無意識に上書きしない。

**再検討条件：** DB、全量同期の書込み範囲、モック、認証・上流負荷まで独立させた実証があり、実行時間が問題になった時にBへ移る。隔離できる読み取り検証と共有状態を変えるケースの実行入口を必要な時点で分ける。並列化のためだけのプラグイン基盤や専用DSLは不要。

## 3. コマンド完了と所有プロセスの回収

公式根拠：[Node.js Child process](https://nodejs.org/api/child_process.html#class-childprocess) のerror／exit／close／killの説明。起動失敗はerrorになり、exitが必ず来るとは限らない。closeはプロセス終了とstdio閉鎖の後に来る。killの送信成功は終了確認ではなく、Linuxでは親のkillだけで孫プロセス終了を保証しない。

**比較した選択肢：** Aは引数配列で直接起動し、起動エラー・終了・出力を一度だけ回収、所有する子だけを停止する。Bはシェルや外部監督機構へプロセス群の管理を委ねる。Bは複雑な既存起動経路に必要になる場合があるが、文字列展開や所有外プロセスの停止を招かない設計が別途必要。単純なデモへ一律導入する利点は小さい。

**採用：** 基本はA。短いコマンドの結果取得ではcloseまで出力を回収し、長寿命サービスではreadyと終了を別々に扱う。errorと終了の多重決着を防ぐ。期限・出力量を制限し、SIGTERM後に実終了を確認してから必要時のみ強制停止する。同期コマンドの終了・業務成功・AWS側処理停止は対象側で区別する。

**具体的な受入：** 実行ファイル不在、実行不可、非0終了、期限切れ、出力上限、通常終了の各経路でPromiseが決着し、残った所有プロセスと一時認証ファイルを回収する。起動途中の失敗でも同じ後処理へ入り、既存MySQL・既存クラスタ・他者プロセスを止めない。ローカルMySQLは専用datadir・socket・PID・ポートを使い、使用しないlistenerも無効化する。

**再検討条件：** 実バッチが孫プロセスや遠隔ジョブを起動し、直接の子の終了だけで回収できなくなった時に、対象固有の停止・確認手順やOSごとのプロセス群管理を追加する。ローカル子終了を遠隔停止に読み替える共通APIは作らない。

## 配置案への反証と評価単位

上記の公式資料は、現在の`tests/scenarios`／`tests/targets`／`test-support`という名前自体を正解とする根拠ではない。配置案A（対象固有知識を共有先へ分離）とB（単一ケース近傍へ置く）は、変更の波及と読みやすさで比較する。

最初の3代表経路では、①ケースから4段階と固定期待値を読める、②対象を変えても共通部へ対象名分岐が増えない、③デモ実装をケースへ直接importしない、④バッチだけを実行してChromeを起動しない、⑤一つの所有変更・失敗・復元を証跡から追える、を評価する。分割で一操作が多くの薄いファイルへ散るならBの近接性へ戻す。同じ業務知識が複数ケースで重複し変更漏れが出るならAへ切り出す。

今回採用するのは小さな寿命管理・通信・実行・記録の仕組みと、その検証である。将来の全対象に対応する比較エンジン、抽象基底クラス、拡張ポイント一式を先に作ることは保留する。耐久性は抽象化の数ではなく、故障時に誤PASSせず所有外状態を壊さず回復情報を残せることから確認する。
