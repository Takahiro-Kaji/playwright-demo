# リポジトリの責務と設計の前提

状態：**第1〜4節は合意済み4論点の整理、第5節は配置の設計提案。** 整理日：2026-10-31（JST）。この記録時点ではコードの移行・実装・AWS実機検証を行っていなかった。既存のフォルダ名を前提にせず、合意した責務から配置とルールを定める。

読む順序は本資料 → [ディレクトリ構成](directory-structure.md) → [設計・実装ルール](design-and-implementation-rules.md)。試験目的と範囲の正本は[分類サマリー](integration-test-overview-onepage.md)、[個別機能の試験方針](integration-test-strategy.md)、[機能横断の試験方針](cross-feature-system-scenarios.md)。本資料群はそれらを実装上の責務・配置・判定に結び付け、試験仕様を再定義しない。

## 1. 管理するもの

| 管理対象 | このリポジトリで持つ責務 | 境界 |
| --- | --- | --- |
| 試験基盤 | 手元PCでの実行、対象への接続、プロセス・モックの制御、証跡と結果の記録 | 業務の正しさは決めない |
| テストケース | 業務条件、操作順序、期待結果、復元計画 | 対象固有のUI・SQL・バッチ・期待値を含む |
| モック | 外部IFの代役と、試験から応答を制御する入口 | ケースが選ぶ応答条件とは分離する |
| デモ用基盤 | 試験対象の実体がない現時点で、試験を動かすための代役アプリ・DB・配置構成 | 業務アプリ本体や将来の実環境インフラではない |

デモ代役アプリを同居させることは許容する。ただし、その実装・専用ヘッダー・DB構造を、将来の実対象や汎用試験基盤の要件にしない。実対象への接続情報と対象固有の操作はテスト側で扱い、業務アプリ本体や将来の実環境インフラの構築ソースを追加する責務は持たせない。

## 2. 共通化する境界

| 共通にする仕組み | 対象固有のまま置く知識 |
| --- | --- |
| ブラウザー起動・寿命管理（標準fixtureを優先） | 画面のlocator、個別操作、期待表示 |
| DBへの接続・パラメーター受渡し・結果取得 | テーブル、SQL、業務キー、関連、有効行・削除の定義 |
| コマンドの起動・終了回収・期限・出力記録 | バッチ名、引数、業務成功・期待異常の解釈 |
| HTTP取得・モック管理APIへの通信 | 上流のURL条件、モック応答の選択、業務HTTP期待値 |
| 証跡の保存・エラーの記録 | UIのlocator・個別操作・期待表示、項目対応・期待データ |
| 比較・差分抽出・判定記録の機構 | 比較キー、NULLの扱い、許容差、業務期待値 |

**共通化の対象は実行・接続・制御・記録の仕組み。** UIの個別操作や業務期待値を共通部に押し込まず、ケースからGiven / When / Then / Afterを読めるようにする。DB接続やコマンド起動のように明白な仕組みから着手し、その他は実際の重複と変更理由を確認してから抽出する。万能DSL、抽象基底クラス、プラグイン基盤は初期条件にしない。

## 3. 実行とデータの前提

- Playwright・Google Chrome、コマンド実行、HTTP・DB照会は手元PCから行う。接続先のアカウント、クラスタ、DB、モック、実対向／デモの区分を実行前に明示する。
- ケースは原則逐次実行。1ケース内の同期バッチとUIの並行実行は必要に応じて行い、最後に両方の終了を回収する。別端末・別実行との共有も考慮する。
- DB変更は許可された非本番の対象範囲だけ。`runId`で証跡や投入行を識別しても、全量同期・共有DB・共有モックの隔離が成立するとは限らない。所有範囲、他の書込み主体、停止・復元手順を決めてから変更する。
- 上流の社内公開データは、社内PCのGit対象外領域に一時保存し、試験終了後に削除する。マスキングやS3を追加要件にしない。認証情報は別管理とし、ソース・ログ・証跡へ書き出さない。

DBの変更前退避、Given後の比較基準、復元結果は別の情報として持つ。全表への無条件restoreを標準機能にせず、復元できないときは後続試験を止め、環境状態を引き継ぐ。詳細は[復元と中断](design-and-implementation-rules.md#3-データの所有範囲と復元)を参照。

## 4. 合否と品質の前提

**PASS・FAIL・未確認を分ける。** 期待した業務上の異常処理はPASSになり得る一方、基盤の故障、照合不能、タイミング不成立を業務PASSに置き換えない。試験の判定と復元状態を別に記録し、cleanup失敗で元の失敗や観測不足を上書きしない。

特に、終了コード0だけで取り込み成功とせず、全件照合で欠落・重複・余剰・宛先違い・値違いを検出する。同期中UIはDB更新との重なりを確認できた範囲だけ判定し、プロセス稼働中だった事実だけでPASSにしない。検証器自体も、既知の故障を混ぜて検出能力を確認する。

試験テーマの必須／任意は[分類サマリー](integration-test-overview-onepage.md)に従う。UI実接続正常、UIモック異常、バッチ実接続正常、バッチモック異常を必須とし、機能横断では全同期成功・一部失敗・不整合・同期中のUI継続を扱う。古い表示は原則許容し、想定外の画面クラッシュ・500・未処理例外・操作不能を重視する。古い情報を使うPOST／PUTは任意、不整合情報を使うPOST／PUTは追加候補で、拒否HTTP仕様を新たに決めない。

## 5. 配置案の選択と再検討

| 案 | 利点 | 負担・リスク | 判断 |
| --- | --- | --- | --- |
| A：ケース・対象固有操作・共通基盤を分ける | 横断ケースがUIとバッチを組み合わせられ、業務知識の境界を追える | 小さい段階ではファイル間移動が増える | **採用案**。対象固有ファイルは必要になった分だけ作る |
| B：対象固有操作をUI／バッチ／横断のケース近傍に置き、共有時に抽出する | 初期の1経路を近い場所で読め、ファイル散在を抑えられる | 横断ケースが必要とするDB準備・復元やUI／バッチ操作の共有先を後から整理する必要がある | 代替案。単一ケースの短い処理には採用案でも許容する |

独立案と反証を比較し、一度再評価した結果、3代表ケースで共有する対象固有知識の置き場としてAを維持する。ただし、最初から表の全ファイルを作らず、Bの利点を取り入れて単一ケースの短い処理は近傍に置く。共通基盤はA・Bのどちらでも接続・制御・記録に限定する。

採用案は、[3つの代表ケース](directory-structure.md#3-代表ケースで配置を通す)が配置・呼出し・4段階・証跡・判定まで説明できることを条件にする。これらを小さく完成させてから共通部分を抽出する。将来、対象固有操作の変更が多数ケースへ意図せず波及する、共通部が対象名で分岐する、実際の重複が蓄積する場合に境界を再検討する。試験目的や合意済みの4論点はその都度再討議しない。

今回の確認は資料上の経路追跡であり、コードの動作・復元可能性・観測可能性を実証したものではない。実装時の品質保証は[結合点ごとの計画](design-and-implementation-rules.md#6-基盤と検証器の品質保証)で行う。
