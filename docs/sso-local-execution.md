[責務と前提](repository-foundations.md)、[配置案](directory-structure.md)、[実装ルール](design-and-implementation-rules.md)を補完する。Given / When / Then / After、手元PCでの実行、インストール済みGoogle Chrome、業務アプリ無改修、デモ用基盤という位置付けを維持する。バッチ専用ケースにChromeを要求しない（別途、認証準備でブラウザーが開くことはある）。

## 1. 難しくなる理由と切り分け

SSOは「ログイン画面を操作できるか」だけの問題ではない。以下の認証境界を分けて選定する。

- **業務UI**：IdP認証後のアプリセッション。Cookie等を再利用できても、IdP・アプリ双方の失効、再認証、権限変更の影響を受ける。
- **試験端末からのAPI取得**：許可されたAPIクライアント、利用者／サービス主体、audience・scope・テナント。UIへログインしただけでAPIへの権限が得られるとは限らない。
- **同期バッチ**：起動者のAWS／Kubernetes権限と、起動先の既存バッチが上流API・DBへ接続する資格を分ける。前者を更新しても後者は更新されない。
- **DB照会・復元**：トンネルへの接続権限とDBログイン権限は別。AWS SSO成功やport-forward存命はDB認証成功を意味しない。

MFA、端末準拠、証明書、統合Windows認証、ブラウザー管理ポリシーなどによって、通常のChromeでは成功しても新しいPlaywright contextでは失敗する可能性がある。IdPの実製品・設定は未確認。Microsoft Entraの[条件付きアクセス](https://learn.microsoft.com/en-us/entra/identity/conditional-access/overview)は端末・利用者等の条件が関わる一例であり、この対象がEntraを使うという意味ではない。

## 2. 対応案と選定順序

以下の順序はこのリポジトリへの**設計提案**。各方式の可否は、管理者が許可する既存の認証経路と最小試行で確定する。SSO全体を独自実装しない。

### A. 対話ログイン後のstorageStateを各ケースへ読込み（UIの第一候補）

専用のheaded Chromeで利用者が通常のSSO・MFAを完了し、アプリへの遷移と利用者・権限を確認してから認証状態を保存する。各ケースは新しいBrowserContextへ同じ準備済み状態を読み込む。ログインの繰り返しを抑えつつ、ケース間のブラウザー状態を分けられる。

[Playwright認証ガイド](https://playwright.dev/docs/auth)と[storageState API](https://playwright.dev/docs/api/class-browsercontext#browser-context-storage-state)を根拠とする。Cookie・localStorage、必要なら対応版でIndexedDBを扱う。sessionStorage、メモリー上の状態、OSや端末に結び付く資格まで再現できる保証はない。保存できてもサーバー側の期限は延びない。状態再利用はSSOログイン経路自体の試験実績には数えない。

採用条件は、状態保存が組織で許可され、新規contextで同一の対象環境・主体・権限を再確認できること。失効・ログアウト・権限変更を試すケースには共有の準備済みセッションを使わず、専用主体／セッションを用意する。

### B. 各ケースの新規contextで対話ログイン（再利用不可時の候補）

保存を禁止される場合や短寿命のセッションでは、ケースのGivenでheaded Chromeを開き、利用者がMFA等を完了する。保存状態に依存せず、ログイン経路を含めて確認できるが、人の待機が必要で無人連続実行には向かない。対話待ちの上限は業務操作のtimeoutと分け、超過は前提不成立で終了する。

ケース間でcontextを引き継がない。IdP側のSSOが残ると画面が省略されることがあるため、新規contextだけで「必ずパスワード・MFAから開始した」と主張しない。IdPまでの完全再認証を試す場合は、その許可された手順と観測根拠を個別に決める。

### C. 自動操作専用の永続Chromeプロファイル（条件付き候補）

必要な認証状態がAで再現できないとき、専用userDataDirを使う方式を小さく試す。端末準拠・証明書・SSO拡張などがそれで動く保証はない。Playwrightの[永続context仕様](https://playwright.dev/docs/api/class-browsertype#browser-type-launch-persistent-context)では普段のChrome既定プロファイルの自動操作は非対応であり、その流用は採らない。

永続contextを複数ケースで使い回すとCookie・キャッシュ等が混ざるため、標準のケース境界とはしない。Aへ安全に書き出せればAへ戻す。書き出せなければケースごとの専用プロファイル作成・対話認証・終了削除が成立するか確認し、成立しない場合は自動試験対象を限定して残りを手動／未確認と記録する。普段のブラウザーへの接続やプロファイル丸ごと複製を解決策にしない。

### D. 公式CLI／SDKの利用者認証（API・AWS操作の第一候補）

既存の認可済みクライアントを使い、ブラウザーでのAuthorization Code + PKCEや、IdPが許可するDevice Authorization等で短期資格を取得する。独自のパスワード収集画面やUIからのトークン抜取りを作らない。根拠はネイティブクライアントの[OAuth認証指針（RFC 8252）](https://datatracker.ietf.org/doc/html/rfc8252)と[Device Authorization（RFC 8628）](https://datatracker.ietf.org/doc/html/rfc8628)。既存クライアント／登録・scope／端末条件が必要で、全IdPで使える方式ではない。

AWS IAM Identity Centerなら公式AWS CLIのSSOプロファイルを使う。これはAWS操作の認証であり、任意の業務API用Bearer tokenの発行手段ではない。

### E. 試験用サービス主体の認証（API・バッチに限定した候補）

対象が既に対応し、運用で許可されている場合だけ、試験専用サービス主体、最小scope、短期資格、公式SDK等を使う。利用者の対話を減らせるが、利用者SSO・委任権限・MFA経路を検証したことにはならない。サービス主体と利用者でデータの可視範囲が違うなら照合条件を揃える必要がある。

試験都合のためのMFA解除、管理者権限付与、長寿命固定tokenの発行、本番アプリのSecret抽出は採用しない。新しいIdP連携や認証バイパスを業務アプリへ追加する前提にも置かない。

### 選定の進め方

1. 非本番で利用可能な主体・既存ログイン経路・端末／VPN／証明書条件と、状態保存の可否を確認する。
2. UIはAを1ケースで試す。再利用不可ならB、必要性が確認できた場合のみCを試す。
3. API／AWSはDを優先し、既存のサービス接続が適切な場合にEを選ぶ。UI CookieによるAPIアクセスは、同じアプリが正式に対応し、同一主体であることを確認できる場合だけ対象固有の接続として扱う。
4. 許可された方法が成立しなければ、対象・理由・代替の手動確認範囲を記録して未確認とする。自動化のためにIdPポリシーを弱めない。

## 3. 安全なログイン準備と保存

準備は、DB・モック・同期処理を変更する前に行う。許可された試験アカウントと権限を使い、正規のアプリURLからIdPへ遷移し、許可済みドメイン・TLS・テナントを確認する。パスワード・MFAコード・パスキー操作・端末承認は利用者が通常の手段で行う。MFA自動承認、OTP seed保存、CAPTCHA回避、証明書検証無効化、認証Cookie改変はしない。

保存先はGit対象外の `.local/auth/<環境>/<主体別名>/`（推奨）または社内端末の専用保護領域。ディレクトリは0700、状態／資格ファイルは0600、Windowsでは同等の本人限定ACLを使う。環境・主体・権限別に分け、他端末・別利用者・別テナントへコピーしない。状態ファイルはパスワードと同等に扱う。保存時刻・既知の期限・確認結果は値を含まない管理情報として分離する。

Gitへ入れてよいのは秘密値のない設定ひな形とファイルパスの指定まで。Cookie、storageState、Chromeプロファイル、Bearer／refresh token、秘密鍵、パスワード、MFA情報、AWSキャッシュをGit・Issue・PR・チャットへ載せない。`.gitignore`は既追跡ファイルを除去しないため、追加差分も確認する。誤登録時は削除commitだけで解決済みにせず、資格を失効・更新し、組織の漏えい対応に従う。

認証準備中はtrace・動画・スクリーンショット・HAR・通信本文の自動保存を無効にする。業務試験中もSSOへ戻る可能性があるため、秘密情報を含まないと確認した証跡だけ保存する。Authorization／Cookie／Set-Cookie、認可コード・stateを含むURL、IdP画面、CLIの生stderr等を無条件に添付しない。除外を保証できない環境では通信トレース等をoffにし、許可項目だけの要約を残す。

**現行デモは失敗時trace・画面保存とHTTP全ヘッダー／本文の証跡があるため、その設定のままSSO実環境へ向けない。** 認証fixtureだけを追加して安全対応完了としない。

## 4. ケースごとの実行契約

### Given

環境・URL・主体別名・必要ロール／テナント／scope・認証方式をケースへ明示し、到達先と照合する。新規BrowserContextへ選択した認証状態を読み込み、既存の読取り専用画面／APIでログイン済みの主体・権限を確認する。URLやログインボタンの不在だけで認証済みとしない。既知の残存期限と予定時間を比べ、不足なら変更前に再準備する。期限不明は成功した疎通確認で代用しても、実行中失効は起こり得ると扱う。

UI・バッチ起動・API・DBの必要な認証を個別に確認してから、データ準備・モック変更へ進む。前提不成立ならWhenへ進まない。準備中も失効し得るため、変更後の失敗はAfterの対象となる。

### When / Then

ケース専用context・APIクライアントを使い、認証更新や権限の切替を業務操作に隠さない。同じ準備ファイルを使ってもcontextを共有せず、ケース終了時の状態で元ファイルを自動上書きしない。同一サーバーセッションは新規contextでも共有し得るので、同時実行・ログアウト・権限変更の影響は別途管理する。原則逐次・`workers: 1`・`retries: 0`を維持する。

未認証・低権限・ログアウト・失効試験には空の認証状態または専用セッションを明示する。異なるロールは別context／主体とし、誤って準備済みの管理者状態を継承させない。これらの認証異常をWhenで意図的に起こすケースだけ、事前に定めた拒否・再ログイン等の期待結果でPASS／FAILを判定する。

### After

途中失敗でも、既存バッチの終了状態と変更範囲を確認し、許可された復元を試みる。context／APIクライアント・ローカルプロセスを終了し、認証状態・専用プロファイルを試験終了時または許可期限到来時に削除する。サーバーのセッション失効／ログアウトが必要なら公式手順で行う。ローカルファイル削除はサーバー失効と同義ではなく、context終了もログアウトとは限らない。

共有の準備済みセッションを各ケースのAfterでログアウトして後続を壊さない。ケース単位のリソース終了と、一連の実行終了時のセッション破棄を分ける。OS・AWSの共有キャッシュを無断で全削除しない。

## 5. 失効・再認証・中断

通常ケースで401、ログイン画面への遷移、IdPリダイレクト、認証関連のCLI／DBエラーを検出したら、対象操作を停止して分類する。403は権限不足や業務上の拒否の場合もあるため、無条件にtoken失効と決めない。HTTP 200のログインHTMLをAPI JSONや上流スナップショットの取得成功にしない。status・最終到達先・Content-Type・期待形式を確認し、資格を別ホストへ転送する自動redirectを許可しない。

公式SDK等の通常の短期資格更新はポリシーと主体／権限が維持される範囲で利用できる。ただし業務POST／PUT・バッチ起動をテスト側で自動再送しない。再認証が必要になったら、人が安全な停止点で行う。

- **When前の失効**：前提不成立／未確認。変更済みならAfterへ進む。再準備後は新しい実行としてGivenから開始する。
- **When以降の予期しない失効**：既に確認した結果を保ち、確認不能な項目を未確認（認証前提喪失）とする。認証問題だけで業務不具合と断定せず、明確な業務不一致はFAILとして残す。
- **同期・更新の成否が不明**：ローカルtimeoutや資格失効で遠隔処理が止まったとはしない。既存の状態確認手段で終了・確定範囲を調べる。認証復旧後も最初から再起動せず、重複更新を防ぐ。
- **復元に必要な認証も失効**：後続変更試験を止め、元の判定に復元失敗／未確認・要復旧を併記。環境、処理識別子、変更範囲、最後の状態、退避先と次の復旧操作だけを引き継ぐ。秘密値は残さない。

同期中UIは、認証を先に完了して操作直前まで準備する。途中にログインが挟まって更新期間との重なりを示せなくなったら、その項目は未確認とする。完了後の正常表示で置換しない。

## 6. 接続先ごとの仕様

### AWS／同期バッチ

AWS CLI v2の[SSOプロファイル手順](https://docs.aws.amazon.com/cli/latest/userguide/cli-configure-sso.html)に従う。以下は既存プロファイルを使った認証確認例であり、AWS構築・配備や同期バッチの起動指示ではない。

```bash
export AWS_PROFILE=approved-test-profile  # 実際の許可されたプロファイル名
aws sso login --profile "$AWS_PROFILE"
aws sts get-caller-identity --profile "$AWS_PROFILE"
```

想定アカウント・role・リージョンを確認し、全ての操作端末／プロセスに同じ選択を明示する。kubectlは対象context・namespace・必要な既存RBACを確認し、port-forwardはloopbackだけに公開する。認証成功を変更権限の確認と混同しない。

AWS CLIが更新可能な資格と、再ログインが必要なSSOセッション失効を分ける。同期の起動は既存コマンドを使い、認証準備を起動・完了待ちに混在させない。実バッチ側の上流API・DB認証の失敗は、既存の終了結果とDB確定範囲で調べる。端末側で再ログインしてバッチ側の問題を解消したことにはしない。

### API／上流GET

試験用の読取り権限、audience・scope・テナント・取得条件を確認し、既存の公式クライアントまたは保護された設定ファイルで資格を渡す。コマンド引数やshell履歴へBearer値を書かない。ブラウザーAPIと同じCookie認証が正式に使える場合、Playwrightの[APIRequestContext](https://playwright.dev/docs/api/class-apirequestcontext)のCookie共有範囲に注意する。`context.request`等はブラウザーと共有するため、独立取得が必要なら別クライアントを作る。

共有／独立のどちらでも別ホストへの資格転送を防ぐ。CSRF等の既存要件を省略しない。単一巨大GETの途中失効・中断・不完全JSONは基準データに採用しない。許可された再認証後に最初から取得し直し、既存方針どおり取得条件・件数・ハッシュ・時間を残す。途中ファイルの結合で完全取得に見せない。

### DB

現行デモは `MYSQL_OPTIONS_FILE` の本人限定ファイルとSELECT専用ユーザーを使う。AWS SSOがDBパスワードを代替する実装ではない。照合の読取り権限とGiven／Afterの変更権限を分離し、接続先・スキーマを照合する。IAM DB認証やDBプロキシを既に採用する実対象では、その公式の発行・更新手順とTLS条件を別途確認する。対応していないDBへ認証方式を追加する前提にしない。

トンネル疎通とDBへの読取りを別々に確認する。新規接続失敗と既存接続の有効性を混同せず、切断・認証失敗時の再接続で書込みやCOMMITを再送しない。トランザクションの確定状態が不明なら調査・復旧へ移る。現行デモの `VERIFY_CA` はホスト名検証を含む方式と同等ではないという既存の制約を維持し、認証を通すためにTLS検証を弱めない。

## 7. 配置と実装の境界

将来の `test-support/` は資格の読込み・寿命管理・安全な状態確認の仕組みを扱う。対象固有のログイン完了画面・主体確認・IdP許可先・API条件は `tests/targets/<対象名>/`、ケースが要求するロールや認証異常の期待値はケースへ置く。秘密値は `.local/auth/` 等へ分離し、証跡の `.local/runs/` やスナップショットへ混ぜない。認証準備の入口は業務ケースの検出対象から外し、対話実行と明示する。

現行 `helpers/`・`scripts/`・CJS配置は今回移動しない。`.env.example`へ未実装のSSO変数や実行できない新コマンドを追加しない。`npm run test:integration:headed` は表示付きの現行デモ実行であり、認証準備機能ではない。無人CIは今回のローカルSSO仕様の対象外とする。

## 8. 実装時の受入条件と残る確認

最初の1ケースで次を確認してから展開する。下記は**未実施の受入計画**であり、今回の文書検証をSSOの動作確認と数えない。

- 正規SSO・MFAの完了後にAの新規contextで期待する主体・ロールを確認できる。不可ならB／Cの選定理由と手動範囲を記録する。
- 別環境・別主体・欠落／破損／失効した状態をGivenで拒否し、DB・モック・バッチへ変更を開始しない。
- ロール違い、未認証ケース、ログアウトケースで他ケースの認証を引き継がず、認証前提と業務結果を分けられる。
- 実行中失効、403、200ログインHTML、許可外redirect、途中GET切断を安全な局所試験で再現し、誤PASS・資格転送・業務操作の自動再送を防ぐ。
- バッチ起動後や復元時の失効でも稼働確認・要復旧・後続停止を残し、元のFAIL／未確認を保持する。
- ダミーの秘密値を使い、失敗時もログ・trace・画面・HTTP添付・CLI例外・Git差分へ漏れないことと、状態ファイルの権限・終了時削除を確認する。

未確定事項：実IdP／プロトコル、試験主体・ロール、状態保存許可、管理端末・VPN・証明書条件、再認証頻度、APIクライアント登録とscope、既存バッチの資格供給・更新、DBの認証方式、復旧時に使える権限。各接続について方式・採否理由・成立証拠・未確認範囲を実装Issueへ引き継ぐ。デモで通っても実IdP・実対象での確認は別に残す。
