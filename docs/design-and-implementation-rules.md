# 設計・実装ルールと品質保証

状態：**新設計提案。既存デモの一部を改善しローカルUI異常1ケースを実証したが、目標構成への移行とAWS実機検証は未実施。** [責務と前提](repository-foundations.md)、[配置と代表3ケース](directory-structure.md)を実装する際の規則を示す。試験範囲と期待仕様は[個別機能](integration-test-strategy.md)・[機能横断](cross-feature-system-scenarios.md)の方針を参照する。

## 1. 依存と命名

- ケース → 対象固有操作 → 共通基盤の向きを守る。ケースから共通基盤を直接使ってよい。共通基盤は対象名で分岐せず、業務SQL・locator・期待値を持たない。
- 横断ケースは対象操作を組み合わせ、別のテストケースを呼び出さない。テストの実行順序や前ケースの残存状態に依存しない。
- 名前は業務目的・作用・観測内容を示す。例：`read-during-sync.spec.ts`、`restoreOwnedRows`、`readActiveRows`。`helper`、`manager`、`common` に責務を集積しない。名前は設計例であり、既存APIではない。
- ディレクトリ・ファイルは `kebab-case`、関数・変数は `camelCase`、型は `PascalCase` とする。業務ケースは `*.spec.ts`、基盤・検証器の確認は `*.test.ts` で分ける。型や命名のためにクラスを導入しない。
- ケースIDは試験目的に対して安定させ、実行ごとの `runId` と分ける。実行IDや環境名を業務キーの代用にしない。
- 期待値はWhen前に固定する。実際の画面・HTTP・DB値から期待値を作って同じ値と比較しない。取込処理全体の複製を期待値生成器にしない。

実行入口と `playwright.config.ts`（設計上の候補名）では、業務ケースの検出を `tests/scenarios/` の `*.spec.ts` に限定し、`tests/verification/` の `*.test.ts` は別の明示的な確認入口へ分ける。原則 `workers: 1`、ケース間の並列実行無効、共有状態を変更するケースの自動retryは無効（`retries: 0`）とし、再実行は復元確認後に行う。同期中UIの並行はケース内部で明示する。バッチ専用ケースはブラウザーを要求せず、UIが必要なケースだけChromeを使う。具体的な設定APIと実行コマンドは採用版の実装時に確認する。

## 2. Given / When / Then / After

| 段階 | 必須の設計内容 | 出力 |
| --- | --- | --- |
| Given | 環境識別、前提・期待値、変更の所有範囲と退避、必要なデータ・モック・UI準備、その成立確認 | 変更前退避、準備後の比較基準、前提確認結果 |
| When | 業務操作・既存同期コマンド、順序・並行・期限、観測開始の位置 | 実行結果、観測時刻、終了を回収する対象 |
| Then | UI／HTTP／DB／バッチの必要な期待照合、全件性、タイミング成立、証拠の不足 | 各検証のPASS／FAIL／未確認と理由 |
| After | 実処理の終了回収、変更済みの設定・データの復元確認、証跡確定、一時データ削除 | 復元状態、後処理エラー、未完了作業 |

Givenが成立しないままWhenへ進めない。試験コード内で4段階が読める形を保ち、巨大な共通フックに業務準備・操作・期待値を隠さない。必要な処理を通常の関数へ分けてもよいが、統一DSLや継承を必須にしない。

Afterは途中失敗・期限切れでも安全な範囲で試行する。ただし端末停止や強制終了時には実行されないため、`finally`だけで復元を保証したとしない。変更前に復旧に必要な識別情報と退避先を記録し、再起動後に環境を確認してから再開・復旧できるようにする。

## 3. データの所有範囲と復元

環境設定には実対象／デモ、AWSアカウント・リージョン・クラスタ／namespace、DB接続先・スキーマ、モックの入口、操作可能範囲を明示する。実行時に到達先と照合し、曖昧な既定値で変更しない。秘密値は設定ひな形と分け、認可されたアクセス手段を使う。

| 対象 | 変更前に決めること | 復元・中断時の扱い |
| --- | --- | --- |
| 限定キーのDB操作 | 所有キー・関連行・許可操作、元に存在した行と投入行、他の書込み主体 | 投入行の除去と既存行の復旧を区別。子親関係・削除方式に従い、対象SELECTで確認 |
| 全量同期 | バッチが更新／削除する全範囲、共有利用者、試験中に他の更新を止められるか、終了後の正とする状態 | 専有できる検証範囲・運用時間を確保。正規の再同期等による復旧を個別設計。確保できなければ変更試験を開始しない |
| 共有モック | 各リージョンの開始時設定、他実行の有無、変更競合・再起動の検出方法 | 自分が変更した分を各々の開始時設定へ戻して実応答確認。競合した状態を旧値で上書きしない |
| 同期プロセス | 起動先、既存の完了・停止確認方法、期限切れ時の停止可能範囲 | ローカル子プロセス終了とAWS側停止を分ける。稼働不明ならDB復元を始めず後続停止 |

ケース逐次でも別PC・別実行との衝突は防げない。共有環境では同時利用しない運用・専有範囲を確認し、`runId`だけで隔離済みにしない。上流全量同期は所有キー外を変更する場合があるため、限定キーの退避だけで復元可能としない。

復元は「元へ戻す」「正規同期後の状態を維持する」「運用の再同期で回復する」など、そのケースの終了状態を先に定める。復元対象外の他者更新を上書きしない。照合は読取り権限、準備・復元は許可された変更権限を分け、全表無条件DELETE／restoreを共通の後処理にしない。

クエリ単位でCOMMITされた更新を、バッチ全体のROLLBACKで戻せる前提にしない。途中失敗時にどこまで確定するかを対象側で扱い、必要な回復とその確認を復元計画へ含める。

復元失敗・実処理の稼働不明・共有状態の競合を検出したら、後続の変更試験を止める。環境・未回収処理・変更済み範囲・最後に確認できた状態・退避先・次に必要な復旧操作を引き継ぐ。復旧用データが必要な間は安易に削除せず、復旧確認後に一時データを削除する。認証情報はこの記録に含めない。

## 4. 観測と照合

### 大量取り込み

単一GETの転送完了、HTTP、JSON解析、取得範囲・件数・バイト数・ハッシュを確認し、不完全ファイルを基準にしない。既存同期コマンドの終了と業務結果を確認してから、DB有効行を上流相当JSONに復元して全対象を比較する。終了コード0だけで合格にしない。

- 業務キーと宛先（テーブル・所属等）で対応付け、欠落・重複・余剰・値違い・誤関連、論理／物理削除漏れを出す。件数一致だけでは不十分。
- BIGINT等の精度を失わない取得・解析・比較方法を選び、数値へ無条件変換しない。NULL・空文字・欠落、文字列結合、有効行判定、DB独自管理列の除外理由を対象側に記述する。
- 配列順は原則意味を持たないという既存方針に従い、キーで正規化する。重複を集合化で消さない。DB順序が偶然一致することを期待しない。
- INNER JOINで孤立行を落とす、Mapで同一キーを上書きする、過剰な正規化で値違いを消す実装を避ける。復元に使った行だけでなく、対象範囲の未対応行・孤立行・余剰行を検査する。
- 一致時のPASSは、取得条件と比較範囲を定めた保存スナップショットとの照合を意味する。実バッチが取得した入力との同一性・完全性は根拠と限界を別記し、未検証の保証を主張しない。取得条件や対象範囲が特定できず比較の妥当性が不明なら未確認。差分時の再GET・ハッシュ比較は[既存方針](integration-test-strategy.md#52-上流データの変化はローカル保存レスポンスのハッシュで比較する)に従い、途中の同一性を証明したとしない。

### 同期中UI

250〜30,000件・クエリ単位COMMITを前提に、まず既存コードからバッチの更新境界とUIの読取り方法を確認する。長めのバッチでChromeを操作直前まで準備し、限定範囲の軽量DB観測とUI参照を試す。観測自体で本来の動作を変えない。

確認対象は、クエリ間のCOMMITを含む**同期によるDB更新期間**のUI継続であり、UIのSELECTと単一SQLの書込み瞬間の一致までは要求しない。プロセス稼働期間、DB観測時刻、UI参照の操作開始〜対象HTTP応答・表示までを別々に記録する。

成立する例の一つは、他の更新主体がいない条件で、UI参照期間内に行った2回の軽量SELECTの間で対象同期に起因するコミット済み状態の変化を確認できた場合である。また、既存の処理ログ・更新時刻から、対象DBの更新期間とUI参照期間の重なりを説明できる場合も成立する。何をどの期間に観測したかを残し、内部SQL同士の同時性まで保証したとはしない。単なるプロセス存命や、UI参照前の最初のDB変化だけでは成立しない。

今回のデモでUI参照期間内の2観測を使う際は、click呼出し前後には操作待ちが含まれるため、実HTTP要求開始から応答完了までの区間に両観測が収まるかを検証した。時刻の分解能とクロックの限界を記録し、成立しなければ未確認とする。

既存観測で説明できなければ、準備済みChromeと軽量SELECTによる簡易試行を行い、未確認として終了する。大がかりな遅延・ロック・観測機構は要求しない。複数APIの間にCOMMITを挟む試験、手動で途中状態を作る試験は別の主張であり、実同期中UIの成立に読み替えない。

古い表示は原則許容し、予期しないクラッシュ・500・未処理例外・操作不能を検証する。同期完了後の正常表示だけで同期中の項目をPASSにしない。具体的な成立条件と追加候補は[機能横断の方針](cross-feature-system-scenarios.md)に従う。

## 5. 判定と証跡

| 記録する軸 | 値の例 | 意味 |
| --- | --- | --- |
| 検証項目の判定 | PASS / FAIL / 未確認 | 必要な前提・証拠で期待と一致／不一致、または判定根拠不足 |
| 理由の区分 | 業務不一致 / 基盤失敗 / 前提不成立 / 観測不足 / 未実施 | 未確認をアプリ不具合や成功に読み替えないための情報 |
| 復元状態 | 不要 / 復元済み / 失敗 / 未確認 | 試験の判定とは独立。実処理稼働不明も記す |
| 実行の終了状態 | 正常完了 / 要復旧 / 中断 | 後続実行を安全に始められるか。業務合格とは別 |

保存スナップショットとDBの不一致は観測上のFAILとして保持する。上流再GETのハッシュ相違または再取得不能により実バッチ入力との対応を確定できない場合、その業務検証項目は未確認（判定保留）とする。比較結果・原因評価・検証項目判定を分け、元の記録を再試験で上書きしない。

各項目を判定してから集約する。独立して確定した業務FAILがあればケースはFAIL、FAILがなく必須項目に未確認があればケースは未確認、必須項目すべてがPASSの場合だけケースPASS。FAILと同時に残る未確認項目も消さない。想定した異常終了・エラー表示はケースの期待を満たせばPASSになり得る。

cleanupエラーは別に追記する。たとえば「ケースFAIL（UI表示不一致）、復元失敗、要復旧」と残し、最初の失敗のスタックや差分を後処理例外で置換しない。「ケースPASS、復元失敗」も実行全体の正常完了ではない。未実施・重なり未確認・照合不能が残る状態を、全試験の完了と表示しない。

独自の判定はPlaywright／CLIの成否へ接続する。必須項目の未確認・FAIL・要復旧は標準実行の成功扱いにせず、実行入口から成功以外の結果を返す。未確認をskipで表す場合も、集約レポートと終了結果で全体PASSを阻止する。例外をcatchして記録しただけで緑にしない。元の失敗・未確認と後処理状態を保存してから結果を確定する。

**最小の証跡**：ケースID・runId・コード版・対象環境・開始終了、Givenと固定期待値、Whenの順序／並行、UI／HTTP／バッチ／DBの必要な観測、全件照合の対象と差分要約、各項目の判定理由・未確認範囲、元の失敗、復元結果と残作業。生データを削除しても判定の対象・方法・限界が分かる要約を残す。社内公開データの一時保存・削除と、認証情報を記録しない前提は[合意事項](repository-foundations.md#3-実行とデータの前提)に従う。

## 6. 基盤と検証器の品質保証

ケース数ではなく **結合点 × 保証する性質 × 条件** で必要な確認を選ぶ。最初に代表経路を準備から証跡保存まで小さく完成させ、局所的なテストではその経路の重要な失敗を検出する。

| 結合点 | 保証する性質 | 条件・故障注入 | 必要な確認結果 |
| --- | --- | --- | --- |
| 環境設定 → DB／モック | 指定した対象だけを変更 | 環境不一致、対象範囲外、共有利用・競合 | 変更前に停止し、誤接続をPASSにしない |
| HTTP取得 → 一時ファイル／JSON解析 | 完全取得だけを基準にする | 途中切断、タイムアウト、不正JSON、正常な空配列 | 不完全は確定しない。空配列は仕様に基づき扱い、無条件の取得成功にしない |
| SQL → JSON復元 → 照合 | 対象全件の欠陥を検出 | 一致例に加え、欠落・重複・余剰・宛先違い・誤関連・値違い・削除漏れを1つずつ注入 | 一致はPASS、故障ごとに期待したキー・差分種別でFAIL。SQLで漏れた行も検出 |
| 値取得 → 正規化 | 型と意味を維持 | 安全整数超のID、NULL／欠落／空文字、配列順変更、重複 | 精度喪失を検出し、許容順序だけ無視、重複を隠さない |
| コマンド起動 → 終了結果 | 完了・業務成功・期待異常を区別 | 終了0だが業務失敗、期待した非0、期限切れ、AWS側稼働不明 | 対象固有の成功条件で判定し、未回収を正常完了にしない |
| DB観測／UI → 重なり判定 | 成立した範囲だけ主張 | プロセスだけ稼働、UIが更新後のみ、証拠欠落 | 未確認。時刻があるだけで成立にしない |
| 失敗 → After → 証跡 | 元の失敗と復元失敗を両立 | UI不一致後にモック復元失敗、DB復元失敗、保存失敗 | 元判定を保持し、要復旧・証跡不足を表示、後続を止める |

小さい既知データの検証は、SQL取得・JSON復元・比較を通して行い、比較関数だけのテストで全件照合完成としない。大量件数では同じ経路の処理時間・メモリ・証跡量を実測する。モック・デモによる局所確認と実対象のAWS受入は別に記録する。

コードから抽出した項目マッピングも、小さい対応表と既知入力で妥当性を確認してから期待値へ使う。元の取込実装を丸ごと写して同じ欠陥を照合側へ複製しない。

## 7. 実装前の確認と完了条件

主な未確認の技術条件は、手元PCから実際の接続先にGETリクエストを送信するための認証手段とアクセス権限である。業務コードから抽出する作業は、起動コマンドの同期性・結果解釈、SQL／キー／項目対応・削除方式、UI読取り・COMMIT境界、利用できる観測根拠。これらを大きな事前調査にせず代表ケースへ反映する。業務上の許容状態・拒否HTTPなど、コードだけで決められない仕様は別途判断する。

実装の完了は、代表ケースの実行だけでなく、故障注入で誤PASSしないこと、停止・復元・証跡の経路が成立することを含む。各必須試験テーマのPASS／FAIL／未確認と復元状態が説明でき、実対象で確認できていない範囲が明示されていることを受入時に確かめる。この資料の経路追跡は、その実装検証の代わりにはならない。

## 8. 実装担当への引継ぎ

ユーザーの運用方針として、統括・設計は **GPT-6 Astra**（要件整理・設計判断・Issue分割・受入条件）、通常実装は **GPT-6.1 Terra Medium** から（Issue実装・必要なテスト追加・PR作成）、難しい実装は **GPT-6.1 Sol Medium〜High**（複雑な改修・難しい不具合）とする。今回の役割分担と実行結果は [初回実装フィードバック](implementation-feedback.md) に記録する。

各Issueでは対象／非対象、具体的な受入条件、環境・共有状態・復元の制約、必要な証跡、未確認事項を渡す。まず代表経路を小さく実装し、実行結果と故障注入の結果を添える。業務期待値、共有状態の所有範囲、観測によって保証する内容など設計判断の変更が必要なら、実装側で暗黙に変えず統括へ戻す。

技術レビューでは依存・復元・判定・証拠の妥当性を確認し、編集レビューでは自然な日本語、論理のつながり、構造化を確認する。編集レビューにはChat側の文書レビューを積極的に利用するが、意味や合意事項の変更は統括が判断し、Chatのレビューで要件を追加しない。通常の機能だけを使い、利用制限の回避は行わない。

### 初回実装からの確認（2026-10-31 JST）

単一モックの原子的な条件付き更新で他者の状態の上書きを防ぎ、所有不明時は復元しない。復元後の実応答と対象別証跡を残し、業務失敗と復元失敗を区別する。初回実装では業務FAILも含め最初の失敗で後続を停止する。独立した後処理時間にも強制終了時などの限界がある。実行結果と未確認範囲は [implementation-feedback.md](implementation-feedback.md) を参照。

バッチ実証では本体期限切れでも同期プロセスの終了を先に回収し、独立したfixture終了処理でDB・一時入力・証跡を扱う。後処理を本体のfinallyへ戻さない。Chromeを使わない実行入口と故障注入入口を分ける。結果と限界は [implementation-feedback.md](implementation-feedback.md)。
